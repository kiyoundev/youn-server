# Issue #10.2: Challenges & Notes

## Potential Challenges

1. **Zero-listing product is a real, reachable state, by design now — not just a crash-recovery edge case.** Superseded from an earlier version of this note (`POST /api/items` used to be chained across separate commits, where a zero-listing product could only happen via a crash mid-chain). Now `POST /api/items` is one request and `urls: []` is an explicitly valid, common input (product created with no listings, e.g. for a caller that adds listings separately via `POST /api/items/{id}/listings`). Either way, the state itself was already null-safe before this issue: `compute_status([])` returns `"paused"` cleanly, `bestPrice([])` returns `null`, existing null-guards in the table already render `"—"`. Worth a quick visual check that an empty badge row doesn't look broken (vs. clearly "no retailers yet"), but not worth a dedicated empty-state component.

2. **`validate_http_url` crashing on `None` instead of failing validation cleanly** — `urlparse(None)` raises `TypeError`, not a Pydantic `ValidationError`, if the guard (`implementation.md` step 2) is missed. Would surface as a `500` on `POST /api/items` with no `url`, not a clean `422`. Straightforward one-line fix, but easy to skip since the existing tests never exercised `url=None` before this issue.

3. **Listing-URL edit re-deriving `retailer`/`scraper_type` silently** — if a user "corrects a typo" in a URL but the hostname actually changes (e.g. fixes `amazon.con` → `amazon.com`, or pastes a different retailer's URL entirely by mistake), the retailer badge changes without an explicit heads-up. Matches `create_listing`'s existing behavior (retailer is always hostname-derived unless explicitly overridden), so it's consistent with the rest of the API — not a new inconsistency, just worth knowing it's not flagged specially in the UI.

4. **Backend contract reopened on a "done" issue** — `#36` is marked ✅ shipped, and its routes were treated as a stable dependency by the original `#10.2` doc text ("against the already-built ... routes"). This plan modifies two of those schemas (`ProductCreate`, `ListingUpdate`) and one route's internals (`create_item`). `ListingUpdate`'s change is purely additive (new optional fields). `ProductCreate`'s is **not** — `url: str` (required) became `url: str | None`, then was replaced entirely by `urls: list[str] = []`; a hypothetical external caller still sending `{url: "..."}` would now get `422` (unrecognized field, since `ProductCreate` doesn't define `url` at all anymore) rather than a graceful ignore. No real consumer exists outside this app's own frontend, so nothing actually breaks — but it's not the additive-only story an earlier version of this note claimed. `#36`'s "done" status now carries a real trailing dependency. Backend tests (step 4, `implementation.md`) are the guard here.

5. **Toast fatigue on the chained add** — with one summary toast per full chain (not per-request), a 5-URL add with 2 failures needs a message that stays readable (`"Item added — 2 of 5 URLs failed: <url1>, <url2>"`). Long URLs could make this toast unwieldy; truncate or link out rather than inlining full URLs if it looks cluttered in practice.

6. **Add-flow design history — settled on bulk after two revisions, stated once for the record.** Surfaced while grilling the add flow's latency (full back-and-forth in the conversation, condensed here): the original design chained N sequential `createListing` requests behind one `createProduct` call, driven entirely by the frontend. A later revision kept that chain but moved it to run in the background after the dialog closed, with a per-product in-flight counter ("Validating N retailers…"), to hide the wait without building true optimistic UI. Both are now **superseded** — see `schema.md`/`implementation.md` steps 2-4, 7. The live design bundles every URL into one `POST /api/items` request; the backend dedups, checks existing URLs, then probes survivors **concurrently** (`asyncio.gather`, bounded by `asyncio.Semaphore(3)`), which N independent frontend-driven requests couldn't safely do (each concurrent request would race the others' duplicate-URL check — safe here because the whole batch is dedup'd in-process, in one request, before any DB write). Net effect: total wait ≈ the slowest single probe, not the sum — fast enough that hiding it behind a background loop stopped being worth the complexity. The old "user closes the tab mid-chain leaves partial listings" scenario no longer applies — there's no longer a multi-request chain to interrupt mid-way; either the one request lands (with whatever succeeded, per `failed[]`) or it doesn't.

7. **Concurrent scraper probing is new to this codebase — verified safe, capped anyway.** No part of this app has driven the scraper concurrently before this issue; the scheduler's own scrape loop (`jobs.py`'s `poll_prices` → `_process_item`) runs strictly sequentially, one listing at a time, deliberately. Before building `create_item`'s concurrent probing, confirmed `PatchrightScraper` uses one shared, persistent, class-level browser **context** (not a new browser process per call) — concurrent pages within one Playwright context is a normal, supported pattern, not an unbounded resource risk. Still capped at 3 concurrent probes (`_PROBE_CONCURRENCY`) as insurance against a pathological large URL paste, on a Pi 5 8GB that's also running every other service in this app's stack — the cap never engages at this app's realistic 1-3 URLs/add.

8. **The DB session sits open (idle) for the duration of the concurrent probes.** `create_item`'s `db: AsyncSession = Depends(get_db)` holds one connection-pool slot from before the probes start until the commit at the end — no queries run *during* `asyncio.gather`, but the connection isn't released either. Not a new risk introduced by this issue (the original single-URL design already held the session across its one `detect_scraper_type` call) and not worth engineering around at this app's request volume (single user, rarely more than one add in flight) — noted so it's a known trade-off, not a silent one, if connection-pool sizing ever becomes a real constraint.

9. **`MissingGreenlet` on `POST /api/items` when every URL in the batch fails validation (or `urls: []`).** Found live, via the UI, against the real local Postgres — the mocked test suite (274 passing tests) never caught it, because mocking `db.execute`/`db.commit` entirely bypasses SQLAlchemy's real lazy-load machinery, which is exactly what this bug lives in. Root cause: `product.listings.append(...)` only ever runs inside `if to_probe:` — when every URL fails the dedup/existing-URL/probe stages, that line never executes, so `product.listings` is never materialized in memory before `db.add(product)`/`await db.commit()`. `AsyncSessionLocal` uses `expire_on_commit=False`, so that's not the trigger — but a relationship attribute that was *never* touched even once still needs its first lazy-load on the next access, and `_build_product_response` accesses `product.listings` synchronously (not awaited), which SQLAlchemy's async dialect can't do outside a greenlet context. Fix: unconditionally `product.listings = []` right after constructing `product`, before any conditional logic — materializes the collection in memory regardless of how many/few URLs survive, so post-commit access never needs a DB round-trip. **Real gap this exposes**: this app's backend tests are 100% mock-based; nothing in the suite exercises real SQLAlchemy ORM behavior (lazy-loading, session lifecycle, greenlet boundaries) end-to-end. Worth a real integration test against actual Postgres at some point — out of scope to build now, noted so it's a known coverage gap, not a silent one.

10. **A completely unrelated pre-existing bug, found and fixed while debugging this issue's row-action dropdown menu — not something `#10.2` introduced, but worth recording here since this is where it surfaced.** `components/ui/button.tsx` lost its `React.forwardRef` wrapper as a silent side effect of running `npx shadcn@latest add toast` back in step 1 (the CLI regenerates shared files beyond just the one requested). The registry's regenerated `Button` assumed React 19's ref-as-prop model; this app runs React 18 (forced by `next: 14.2.35`, which doesn't support React 19 at all). Under React 18, that dropped `ref` silently never reached `@base-ui/react`'s `Button` primitive — no error, no console warning anywhere. Harmless for `Button` alone, but broke any Base UI `Trigger`/`Close` using `Button` as its polymorphic anchor (`render={<Button/>}`) — the trigger's own local state (hover, `aria-expanded`, `data-base-ui-inert` on `<main>`) still looked correct, only the actual popup silently never mounted. Cost real time to isolate specifically because every layer stayed silent — no thrown exception, no dev-overlay error, no console output at any point. Fixed by restoring `forwardRef` in `button.tsx` (one shared file, fixes every instance app-wide, including a second latent case in `dialog.tsx`'s `DialogPrimitive.Close` that hadn't been exercised yet). Full writeup and the general risk pattern (for future `shadcn add` runs) in `.doc/architecture.md`.

## Key Differences

| Aspect | Current (`#36`) | Target (`#10.2`) |
|--------|------------------|-------------------|
| Proxy route | `GET` only | `GET`/`POST`/`PATCH`/`DELETE` via shared `relay()` |
| `POST /api/items` | `url` required (singular), creates 1 listing atomically, probe blocks the request | `urls: list[str]` (bulk), every URL probed **concurrently** (bounded), partial success returned as `{product, failed[]}` instead of erroring the whole request |
| `ListingUpdate` | `active` only | `active`, `url`, `retailer` |
| Pause/resume | Doesn't exist in UI | Per-listing toggle in the sheet (not row-level, per grill-me resolution) |
| Update strategy | N/A (read-only) | Await response → `mutate()`, no optimistic updates (bulk add makes this cheap — one request, not a chain) |
| Error surface | Page-level fetch-failed banner only | `@base-ui/react/toast` toasts per mutation, plus the existing banner for the initial load failure |
| Delete | N/A | Confirm dialog (product only); sheet auto-closes if its product is deleted |

## Rollback Plan

1. Revert the frontend commit(s) — `watchlist/page.tsx`, `layout.tsx`, `lib/api/items.ts`, `lib/toast.ts`, `components/ui/toast.tsx`, proxy route — restores the read-only `#36` state (mock-stub write paths return, no functional loss since none of these paths worked before this issue).
2. Revert the backend commit(s) — `ProductCreate`, `ListingUpdate`, `items.py`, `validators.py`. No Alembic migration is introduced by this issue (no new columns, only Pydantic schema fields and route logic), so there's no migration to undo either way — but note `ProductCreate`'s change (`url` → `urls: list[str]`) is not purely additive (challenge #4), so this is a real revert, not just deleting new-and-unused code.
3. No dependency to uninstall — `@base-ui/react` predates this issue and other components still use it; removing `components/ui/toast.tsx` alone fully backs out the toast piece.
4. Verify: `GET /api/items` (already-shipped path) still works unmodified after rollback — confirms the revert didn't touch anything `#36` depends on.
