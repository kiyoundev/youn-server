# #36: Challenges & Notes

## Potential Challenges

1. **Connection lifecycle leaks across three separate hops** — browser↔proxy, proxy↔backend, and backend's fan-out-set membership are three independent connections, not one continuous pipe. Nothing automatically propagates a close from one hop to the next. If the proxy's streaming handler doesn't watch the incoming request's abort signal and close its own outbound backend connection on browser disconnect, or if the backend doesn't notice its connection died and deregister itself (see #8 — built as an active ping/write-and-catch, not a passive `is_disconnected()` check), connections/fan-out entries leak silently — invisible in a quick manual test (one tab, open, close, done), only surfaces under real usage (many open/close cycles over a session). Mitigate: explicit disconnect-detection at both hops (Implementation steps 1 and 2), and the StrictMode rapid-mount/unmount manual test specifically targets this.

2. **Reconnect recovery is table-only, not history — accepted, documented limitation.** The `onopen` safety-net refetch (`mutate("/api/proxy/items")`) corrects the table immediately on reconnect, but does **not** refresh any listing's price-history cache — `mutate()` only touches the exact key it's given, and SWR has no concept of "related" keys. A listing rescraped *during* a disconnect will show a correct price/status in the table but a stale sparkline until its *next* real scrape broadcasts normally. Low-stakes (cosmetic, self-heals within one scrape cycle), deliberately accepted rather than fixed — see `.doc/issues.md` `#36` for the full reasoning. Revisit only if this proves noticeable in practice.

3. **Day-bucketing must happen before merging per-listing histories, not after.** `_process_item` scrapes listings sequentially, so two listings' `checked_at` timestamps for "the same" scrape cycle will differ by seconds to minutes — never exactly equal. Both the sparkline's min-merge (`productPriceHistory()`) and the chart's row-building key on exact date-string equality; without bucketing first, every bucket ends up holding exactly one retailer's point, silently degrading "min across retailers" to "whichever listing happened to be scraped at that instant" and breaking the multi-line chart's overlap. Decided: bucket by **local calendar day**, client-side, via `Date`'s local-aware methods — not UTC-day (would need no conversion but reads oddly against the user's own clock) and not backend-side (would need a new timezone config value for no real benefit, since the browser already knows its own timezone for free).

4. **React StrictMode double-invoke (dev-only) can mask or create connection bugs.** `useEffect`'s setup→cleanup→setup double-fire in local dev could open two `EventSource` connections briefly if cleanup isn't airtight — a bug that would never surface in a production build, making it easy to miss during testing unless specifically checked for. Called out as its own manual test step (Implementation step 6) rather than assumed covered by general cleanup work.

5. **This design assumes a long-running server process — breaks on serverless.** Both the Next.js and FastAPI processes need to hold connections open indefinitely. True for this app's actual deployment (Docker Compose on the Pi, persistent containers) but would break outright on a serverless host (Vercel route handlers, AWS Lambda) due to hard per-request execution time limits. Not a current risk, but a real constraint if the frontend's hosting model ever changed — worth remembering rather than rediscovering later.

6. **`EventSource` cannot carry the `X-API-Key` header — resolved via existing proxy pattern, not a new problem.** The browser's `EventSource` API has no `headers` option. This is a non-issue here specifically because the browser was never going to carry the secret regardless (same BFF/proxy pattern as every other route) — the key is attached on the proxy's own separate outbound `fetch` to the backend, a leg never constrained by `EventSource`'s limitations in the first place. Documented in `.doc/keynotes.md`'s API Proxy Pattern section for the full reasoning, in case this comes up again on a future streaming route.

7. **Browser's per-origin connection cap (HTTP/1.1) — real, confirmed live on this deployment, resolved via leader election.** Chrome/Firefox cap concurrent connections to one origin at 6 under HTTP/1.1 — `EventSource` connections count against that same budget as every other request to the origin (proxy fetches, images, etc). Confirmed this stack is actually exposed to it: `docker-compose.yml` has no TLS/reverse-proxy in front (plain `backend:8000`/`frontend:3000`), so no HTTP/2 multiplexing to sidestep the cap. A 7th open tab of `/watchlist` would silently never receive live updates — no error thrown, `EventSource` just queues behind the cap. Three options considered:
   - **Accept as-is** — realistic tab count for a personal single-user app is low, unlikely to hit 6. Rejected as final answer once leader election turned out cheap to build (~30-40 lines).
   - **SharedWorker** — one shared JS context across all same-origin tabs, holds the single real connection, no election logic needed at all. Ruled out: no `SharedWorker` support on iOS Safari, ever (desktop Safari got it in v16/2022, iOS never has) — would silently break the feature on iPhone with no fallback.
   - **BroadcastChannel + Web Locks leader election (chosen)** — every tab calls `navigator.locks.request("sse-leader", ...)`; browser's lock queue guarantees exactly one holder, auto-promotes the next queued tab when the leader tab closes/crashes (no heartbeat/staleness-timeout code needed). Leader holds the real `EventSource`, relays messages to followers via `BroadcastChannel`. Broadly supported incl. iOS Safari 15.4+. Implementation: `implementation.md` §6.
   - Infra-level fix (put HTTP/2 in front, e.g. `tailscale serve` given Tailscale's already in this network) was also discussed and would remove the cap entirely with zero app code — set aside as out of scope for this issue (infra decision, not app decision), worth revisiting independently. Full comparison: `.doc/keynotes.md`.

8. **Disconnect detection: ping/write-and-catch, chosen over `is_disconnected()` alone and over the `sse-starlette` library.** Three options considered for detecting a dead SSE connection server-side:
   - **`await request.is_disconnected()`, polled periodically** — a passive read of a flag the ASGI layer sets *only if* it received a clean disconnect signal (a FIN packet). Structurally blind to silent deaths (wifi drop, laptop sleep, dropped NAT mapping) — no signal ever arrives, so the flag never flips, and the check reports "still connected" indefinitely. Rejected as the sole mechanism for exactly this reason, though it was the first version built (see the superseded description this replaced above).
   - **`sse-starlette` (third-party library)** — `EventSourceResponse` with a built-in ping interval, would've solved the same problem with less hand-rolled code. Rejected: this issue's `context.md` explicitly commits to zero new dependencies (native browser/stdlib APIs only), and pulling in a library reverses that deliberately-made decision for a problem solvable in ~10 lines without one.
   - **Ping/write-and-catch (chosen)** — on each idle timeout (`_PING_INTERVAL` = 15s), `yield ": ping\n\n"` instead of asking a question. A silent-dead connection looks identical to a healthy idle one under a passive check; only an actual write attempt gives the OS a chance to eventually notice the peer is gone and report the failure. No explicit `except` needed to act on that failure — Starlette tears the generator down via `GeneratorExit` (a `BaseException`, not an `Exception` — an earlier draft's `except Exception: break` wouldn't have caught it), and the existing `try/finally` around the loop already calls `sse.unregister(queue)` regardless of exception type.
   - **Caveat, not fully solved by any of the three:** a write to a dead socket isn't guaranteed to fail on the very next attempt — TCP can silently buffer into the local send queue for a while before the OS's own retransmission timeout exhausts and finally surfaces the error (can exceed the 15s ping interval, depending on OS TCP tuning). "Eventually detects it, more reliably than a passive check" is the accurate claim — not "detects it within one ping interval, guaranteed."
   - **Separately, home-server power outages are out of scope for all three options** — a dead backend process runs no code at all, so nothing server-side can detect its own death. That case is handled entirely by the frontend's reconnect/backoff logic (Implementation §5), unrelated to this decision.

## Key Differences

| Aspect | Current (rest of this repo) | Target (this issue) |
|--------|------|--------|
| Update trigger | `useSWR(..., { refreshInterval: 30000 })` — short polling | `EventSource`, server-pushed, no interval |
| Reconnect | N/A (stateless polling, nothing to reconnect) | Manual exponential backoff (copies `FinnhubClient._listen()`'s existing pattern) |
| Proxy handler shape | One-shot `fetch` → `await res.json()` (`[...path]/route.ts`) | Streams chunks, never buffers/awaits completion (`events/stream/route.ts`, new) |
| Backend event delivery | `Event` DB row + `asyncio.Queue`, alert-worthy only | New unconditional in-memory broadcast, sibling to the existing alert path, not a consumer of it |
| Missed-update recovery | N/A | `onopen` safety-net refetch (table only, not history — accepted gap) |
