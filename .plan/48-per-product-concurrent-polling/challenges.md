# Issue #48: Challenges & Notes

## Potential Challenges

1. **`close_if_idle()` call-count mismatch after moving `_dispatch_first_scrapes`** — the moved helper today calls `close_if_idle()` once per invocation (once per request in #41's case). `poll_prices` will call the dispatch logic once *per product*, but needs `close_if_idle()` only once per *whole cycle*. Naively reusing the moved function as-is per-product would reintroduce the exact open/close thrashing the current code's comment explicitly warns against. Mitigation: split gather-only vs gather+close responsibilities (see `implementation.md` Phase C) so `items.py`'s two call sites keep today's per-request close, and `poll_prices` gets a single cycle-end close.

2. **Lock ordering / deadlock risk from `with_for_update()`** — each `process_item` transaction locks at most one `Product` row (never two), and never locks a `Listing` row via `FOR UPDATE`. No transaction acquires locks in a different order than another, so no circular-wait is possible. Worth a quick sanity check during implementation that no other code path (e.g. a future admin edit endpoint) takes a `Listing` lock before a `Product` lock while `process_item` does the reverse — none exists today.

3. **Lock wait time under real concurrency** — with the fix, a product's own listings serialize at the tail (alerted_at check → commit) instead of running fully in parallel end-to-end. For 3 listings this is a few short DB round-trips, not scrape time, so the wall-clock cost is expected to be small — but worth confirming with the before/after timing measurement (AC #6) that the *scrape* concurrency gain isn't quietly offset by lock contention on high-listing-count products.

4. **Identity-map staleness if the early `Product.active` check and the later `with_for_update()` load aren't kept separate** — this is the one genuinely subtle bug risk in the whole change, flagged by review before any code was written. `process_item`'s early bail (Phase C) and the alert-dedup fix (also Phase C) both read `Product` in the same function, same session. If the early check used `session.get(Product, ...)` (a full entity load), SQLAlchemy's session identity map would cache that instance; the later `with_for_update()` locked `select()` can then hand back the *same cached object* instead of a fresh post-lock row — meaning the lock is genuinely held, but the Python-level `product.alerted_at` value being checked is stale (read before the lock), silently reintroducing the exact double-alert race this issue exists to fix, just relocated. Mitigation (already reflected in `schema.md`/`implementation.md`): the early check is a **column-only** `select(Product.active).where(...)` — never a full entity — so it never populates the identity map, and the later locked load is guaranteed fresh.

   **What actually verifies this, and what doesn't:** a genuine end-to-end unit test was attempted (two `process_item` calls under `asyncio.gather`, sharing a mocked lock/DB state) and deliberately dropped after it demonstrated a false sense of coverage — it passed *identically* whether or not the lock/`with_for_update()` was simulated at all. Root cause: there's no `await` between `if product.alerted_at is None` and `product.alerted_at = now` in `process_item`, and Python's single-threaded event loop only preempts at real `await` points — so no combination of mock-injected yields can slip a second task into that specific window; whichever task's resume reaches that region always runs it to completion atomically before the other task's resume is even processed, lock or no lock. A test built to demonstrate the race regardless would only be asserting a hand-coded fixture's fidelity to Postgres, not this code's correctness — worse than no test, since a green result reads as "the race is covered" when it isn't. What's unit-tested instead (`test_process_item_writes_history_and_price_drop_event`): `process_item` asks for the row lock at all (`stmt._for_update_arg is not None` on the second `session.execute` call) and does so exactly once, via `session.execute`, not a plain `session.get(Product, ...)` (`session.get.await_count == 1`, covering only the `Listing` load) — this is what actually breaks the moment someone reverts the fix or reintroduces a second unlocked read. The race itself — genuine concurrent transactions serializing correctly — is only verifiable against a real Postgres, which is exactly what this issue's AC already requires: `_index.md`'s "verified live with a product having 2+ listings that both cross target price in the same cycle, confirming exactly one Event/notification fires." That live check is the actual proof; the unit tests are a regression guard on the SQL shape, not a substitute for it.

5. **`session.get()` → `select().with_for_update()` changes error behavior on missing row** — `session.get(Product, id)` returns `None` if missing; `scalar_one()` raises `NoResultFound` if missing. `listing.product_id` should always reference a live `Product` (FK), but if that invariant is ever violated (orphaned listing), the failure mode changes from a silent `None`-then-`AttributeError` further down to an explicit exception at the query — arguably an improvement (fails louder, closer to the cause), but worth noting since it changes what `_bounded_process_item`'s backstop catches.

6. **Moving code owned by #41 risks regressing a working feature** — `_bounded_process_item`/`_dispatch_first_scrapes` are the exact mechanism #41 already ships and depends on for add-time first-scrapes. A pure cut-and-paste with import-swap (not a rewrite) plus the #41 regression re-test in `implementation.md`'s Testing & Validation section is the guard against this. (Already done — see `implementation.md`'s "Completed" section.)

7. **Dropping `Listing.active` deletes a real, tested capability, not just unused schema** — surfaced and confirmed with the user before proceeding (not silently assumed): `backend/tests/scheduler/test_jobs.py::test_process_item_ignores_inactive_sibling_listing_when_recomputing_cheapest` and several cases in `test_product_status.py` specifically exercise one listing paused while its sibling stays active. No UI ever exposed that independence (the only control is one product-wide Switch), but the backend modeled and tested it. Consolidating to `Product.active` means: (a) those tests get deleted, not adapted — the scenario they cover can't happen anymore; (b) the only way to stop scraping one permanently-broken retailer URL becomes deleting its listing outright, which cascades its `PriceHistory` (`cascade="all, delete-orphan"` on `Listing.price_history`) — there's no longer a non-destructive way to "soft-disable just this one bad URL." User chose this tradeoff explicitly after seeing it stated.

8. **Migration backfill correctness depends on a point-in-time check, not an invariant** — the "every product today is fully-active or fully-inactive" fact was confirmed by a live query against production data at planning time, not enforced by any constraint before this migration runs. If a listing gets independently toggled between now and when the migration actually runs (via direct API call, not the UI — the only path that could produce a mixed state), the backfill would still run without error, but that listing's individual pause state would silently collapse into whatever the majority of its siblings were. Low risk (requires a non-UI actor), but worth re-running the same diagnostic query immediately before running the migration for real, not just once during planning.

## Key Differences

| Aspect | Current | Target |
|--------|---------|--------|
| Active/paused state | `Listing.active` (per-listing bool), `Product` status *derived* from all listings | `Product.active` (real column), `Listing.active` removed entirely |
| `compute_status` | Scans listings for "any active" to determine paused | Reads `product.active` directly |
| Pause UI action | 1 Switch → N `updateListing` calls (`Promise.allSettled`) | 1 Switch → 1 `updateProduct` call |
| Soft-disable one bad retailer URL | Possible (`PATCH .../listings/{id}` with `active: false`) | Not possible — delete-only, cascades price history |
| `poll_prices` query | Flat `select(Listing.id)`, no grouping, filters `Listing.active` | Grouped by `product_id` (client-side dict), filters via a `Product.active` join |
| Per-product scraping | Sequential, single listing at a time, no ordering guarantee | Concurrent within a product (bounded semaphore), products still sequential |
| `process_item`'s early bail | `if not listing or not listing.active: return` | `if not listing: return` + column-only `Product.active` check |
| `process_item`'s Product read (alert-dedup) | `session.get(Product, id)` — plain, no lock | `select(Product).where(...).with_for_update()` — row-locked |
| `_bounded_process_item`/`_dispatch_first_scrapes` location | `items.py` only, #41-specific | `jobs.py`, shared by both `items.py` (#41) and `poll_prices` (#48) |
| Concurrency pools | One (`_first_scrape_semaphore`, items.py) | Two, separate instances, same cap value (3) — `items.py`'s and `jobs.py`'s own |
| Double-alert race | Latent, unfixed | Fixed at the single `process_item` read-then-write site |

## Rollback Plan
1. **Code (Phases B/C, non-schema):** `git revert` the relevant commit(s) — pure application logic, no data involved, clean revert.
2. **Schema (Phase A, migration `0012`):** `cd backend && uv run alembic downgrade -1` before reverting the code — the model/route/schema changes assume the column exists, so downgrade the DB first, then revert the code that depended on it. Note the downgrade is **not** fully lossless (see `schema.md`'s `downgrade()` — every listing comes back `active=true` regardless of its pre-drop value, since that granularity was already discarded by `upgrade()`). Acceptable for a rollback path; not a concern for the forward migration itself (confirmed lossless there).
3. Verify: single-listing `poll_prices` behavior, #41's add-time flow, and the watchlist pause Switch all return to their pre-#48 behavior — confirmed by re-running the same manual tests from `implementation.md`'s Testing & Validation section against the reverted state.
